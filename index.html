The friction

Branch switching is a context switch.

A normal checkout replaces the files in your working directory. That is inconvenient when a feature is half-built and an urgent task arrives.

The mental model

One Git database. Several checked-out views.

The shared part: object database, refs and the common repository history.

The separate part: each worktree has its own files, HEAD and index.

The practical result: a branch can stay open in its own directory while you use another one.

Working files

Each directory exposes one checked-out revision and its own index.

A linked worktree normally contains a .git file that points to its administrative directory; it is not a second independent clone.

The starting move

Add a directory and a branch together.

  1. Choose a sibling path. Keeping worktrees beside the main checkout makes them easy to spot and remove.
  2. Create a branch from a base. -b creates the branch if it does not exist.
  3. Open that path in your editor. It behaves like a normal checkout.
# while inside shop/
git worktree add -b feature/search ../shop-search origin/main

A useful pattern

Use worktrees for genuinely parallel tasks.

The benefit is not “more branches.” It is preserving the state of more than one branch at a time.

The guardrail

Git protects a branch from being checked out twice.

Normally, one branch has one active worktree. This avoids two directories independently changing the same branch’s HEAD and index state.

What to do instead

Create another branch for the other task, or use a detached worktree when you only need to inspect a commit.

Why it matters

Worktrees make parallel editing safer by default. Do not defeat the protection just to reuse a branch name.

A small lifecycle

Add. List. Remove. Prune when needed.

git worktree list shows the registered paths and revisions.

git worktree remove <path> removes a clean linked worktree; Git protects modified or untracked work unless forced.

git worktree prune clears stale administrative records after a directory has disappeared outside Git.

git worktree list
/code/shop a18c… [main]
/code/shop-search c42e… [feature/search]

git worktree remove ../shop-search

git worktree prune # only if records are stale

# an existing branch, if not checked out elsewhere
git worktree add ../shop-hotfix hotfix/login

# inspect a commit without a branch
git worktree add --detach ../shop-bisect v2.4.1

# make a worktree resistant to automatic pruning
git worktree lock --reason "external drive" ../shop-bisect

Match the tool to the job

Three useful variants.

Existing branch: reopen work that already has a branch.

Detached: build, test or investigate a specific commit without creating a branch.

Locked: tell Git not to prune a worktree that is temporarily unavailable.

Constraints worth remembering

A worktree isolates files, not every kind of state.

Dependencies

Each directory has its own files.

Expect to install dependencies, build generated files or create local environment files in each worktree as your project requires.

Ports & services

Running processes can collide.

Two copies of the app may compete for the same port, database, cache or temporary directory.

Configuration

Shared config is still shared by default.

Use care with repository config and tooling that writes outside the worktree. Git supports per-worktree config when enabled.

The takeaway

Keep the work that matters open.

Git worktrees reduce branch-switching friction by giving parallel branches independent directories while retaining one shared repository history.
